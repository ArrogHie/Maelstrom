# W2 订单簿效率压测报告

> 压测程序：[`bench/stress_order_book.cpp`](../bench/stress_order_book.cpp)（AI 隔离编写，不参与 `include/`、`src/`）。
> 被测对象：W2 手写 `OrderBook`（`src/order_book.cpp`）。
> 环境：WSL2 / AMD Ryzen 7 255H / 16 核 / Clang 18 `-O3 -DNDEBUG -march=native`，CPU 绑核。
>
> ⚠️ 三个必须知道的前提，否则数字会读错：
> 1. **必须 Release**。`build/` 是 Debug，其数字无意义；本报告全部用 `-O3 -DNDEBUG`。
> 2. **WSL2 噪声大**。同一项反复跑，离散度可达 1.6–2.9×。报告用多轮**中位数**，单次数字只当趋势。
> 3. **不是 W7 的正式基准**。这是 W2 的"体检"，目的是找瓶颈、验证复杂度，不是简历数字。

## 二、核心结论（先说最重要的）

1. **O(1) 目标达成。** `best_bid`/`best_ask` 在 N=1 万→400 万区间恒定 **~2.5–3.5 ns**，完全不随规模增长——`map.begin()` + 链表头，符合设计。
2. **瓶颈是堆分配，不是数据结构。** `add` 每单要 **2 次 malloc**（`unique_ptr<OrderNode>` 一个、`unordered_map` 哈希节点一个），耗时 **70–340 ns** 全被分配吃掉。对照实验：pmr 单调缓冲分配 **4.3 ns** vs glibc **41.5 ns**，**约 10×** 差距——这就是 W6 自定义 arena 的收益空间。
3. **相对 O(n) 基线是数量级碾压。** 同样操作，`best_bid` 快 **~38 万倍**、`cancel` 快 **~2000 倍**（N=100 万，各 10 万次）。数据结构选型的故事立得住。
4. **极端负载下结构不变。** 200 万次随机增删改后，`size/find/best_bid/best_ask/quantity_at` 全部与实际状态一致；清空后无残留（无空价位、无悬挂）。这部分由 `endurance` 模式验证。
5. **README 的 10M orders/s 目标当前未达到**（混合负载约 **4.7M ops/s**），但那是 W7 的目标，且当前未做任何分配器/布局优化——**瓶颈已定位、路径清晰**，不是设计缺陷。

## 三、吞吐（N=1,000,000）

| 场景 | ns/op | M ops/s | 说明 |
|---|---|---|---|
| add 同价深队列 | ~70–340 | 2.9 | 全被 2 次分配主导；深队列本身是 O(1) 尾插 |
| add 海量独立价位 | ~665 | 1.5 | 更贵：多一次 `std::map` 插入（O(log L)）+ 分配 |
| **cancel FIFO（撤队头）** | **~34–59** | **29.6** | 纯 O(1) 摘链，最接近"数据结构真实成本" |
| cancel 随机（摘中间） | ~440–800 | 1.8 | 随机访存 cache miss + 释放，波动最大 |
| **modify 同价改量** | **~8–59** | **129** | 最快路径：只改差值，无分配无摘链 |
| modify 改价（撤+挂） | ~132 | 7.6 | = cancel + add，含一次释放+一次分配 |
| 查询 best_bid+ask×2 | ~5.3 | 190 | O(1) 实证 |
| 查询 quantity_at | ~22 | 46 | 两次 `map.find`，O(log L) |
| 随机混合负载 | ~211–366 | 2.7–4.7 | 55% 挂/30% 撤/10% 改量/5% 改价 |

## 四、复杂度扫描（验证 O(1) / O(log L)）

| N | add(同价) | add(新价位) | cancel(随机) | **best_bid** |
|---|---|---|---|---|
| 10,000 | 60.4 ns | 178.3 ns | 91.8 ns | **2.6 ns** |
| 100,000 | 69.6 ns | 262.6 ns | 152.8 ns | **2.5 ns** |
| 1,000,000 | 72.2 ns | 469.6 ns | 439.5 ns | **2.5 ns** |
| 4,000,000 | 236.5 ns | 666.7 ns | 538.6 ns | **2.5 ns** |

- `best_bid` 恒定 → **O(1) 确证**。
- `add(新价位)` 随 N 增长 → 符合 `std::map` 的 **O(log L)**（L=价位档数）。
- `add(同价)` 前三级平稳（O(1) 尾插），4M 处跳到 236ns → 工作集超出 cache/TLB，属**内存层次**效应而非算法退化（数据结构本身仍是 O(1)）。

## 五、延迟分位数（逐次 rdtscp，N=100 万）

| 操作 | p50 | p90 | p99 | p99.9 | max |
|---|---|---|---|---|---|
| 空操作（测量地板） | 30.1 | 30.1 | 30.1 | 50.1 | 67265 |
| add（同价档已存在） | 70.1 | 80.1 | 130.2 | 200.4 | 4.5 ms |
| add（新价位） | 310.6 | 410.8 | 3767.0 | 9056.8 | 23.8 ms |
| **best_bid** | **30.1** | **30.1** | **50.1** | 50.1 | 127 µs |
| cancel（随机） | 470.9 | 621.2 | 901.7 | 2735.1 | 789 µs |

**读法提醒**：每行的 p50 都压在 ~30ns 的"测量地板"上，说明**计时本身有 ~30ns 固定开销**（`rdtscp` + 寄存器保存）。真正的算法成本要看 p50 减去地板，以及 p99 的尾部。`max` 动辄毫秒级，是 WSL2 调度/页错误造成，不是代码问题——这也是为什么尾部延迟必须在**裸机或隔离核**上测才有意义（W7 的注意点）。

## 六、内存占用

| 规模 | 堆占用 | 字节/单 |
|---|---|---|
| 100 万单 / 1000 价位 | ~121 MB | **123.7** |
| 100 万单 / 100 万价位 | ~214 MB | **219.6** |

理论下界：`Order`(32B) + 2 指针 + level 指针 ≈ 56B，加 `unordered_map` 哈希节点 ≈ 40B，再加 100 万价位时的 `map` 节点 ≈ 80B。实测与估算吻合，说明**没有明显泄漏或浪费**；但"每单 2 次独立分配"带来的**分配器元数据 + 指针跳转**正是 W6 要消灭的目标（arena 可把节点紧凑放置，同时改善 cache 局部性）。

## 七、给 W6/W7 的优化线索（按收益排序）

1. **arena / pool 分配器**（收益最大）：把 `OrderNode` 与哈希节点从"每单 2 次 malloc"改为池化分配。分配本身 41.5→4.3ns，且内存连续后 cache 命中率提升，`add`/`cancel(random)` 会同步受益。
2. **减少每单分配次数**：`unordered_map<OrderId, std::unique_ptr<OrderNode>>` 是"指针的指针"。可考虑节点本体内联存储，或在 arena 上开 `unordered_map` 的节点分配器。
3. **`map.emplace` → `try_emplace`/`find`**：当前写法即使价位已存在也会构造一个 `Level` 再丢弃（实测空转 ~6ns vs `find` 1.8ns）。深队列场景下这是纯浪费。
4. **`std::map` → 有序结构/跳表/自定义价位索引**：若 L 很大（本测试 100 万价位时 `add` 涨到 666ns），`O(log L)` 会显现；W7 可对比。
5. **`Level` 里冗余存 `price`/`side`**：map 的 key 已经是 price，可省。

## 八、本次压测修正的两个自身错误（记录方法学教训）

压测程序第一版有两个**假数据**，值得记下来，因为它们是性能测量的经典陷阱：

1. **同进程内连续测量互相污染**：第一版在**一个进程**里依次测 `make_unique`、`unordered_map::emplace`、真实 `add`，结果 `add` 只报 104ns——因为前面的测试已经把分配器空闲链表、TLB、cache 都预热了。改成**每项独立进程**后，`add` 的真实值是 ~300ns。**教训：测量项之间必须隔离，否则测的是"热缓存下的最好情况"。**
2. **在错误的对象状态上测量**：复杂度扫描里 `best_bid` 被放在"撤空之后"的行上，量到 2.7ns 的空簿早退路径。修正到"有单的书"上后仍是 ~2.5ns，但这个数字**只是碰巧对**——方法错了，结论就不能信。**教训：测之前先断言被测对象处于预期状态。**

## 九、结论

W2 的订单簿**在算法层面达标**：所有声称 O(1) 的操作经 N 从 1 万到 400 万的扫描验证确实恒定，跨价位操作符合 O(log L)，相对 O(n) 基线有 3–5 个数量级的优势，且在 200 万次极端混合负载后结构不变量依然成立。

**性能上限目前由内存分配决定**，不是数据结构。这恰好是 W6 的用武之地——把"每单 2 次 malloc"换成 arena，是本项目从"正确"走向"低延迟"的第一刀。
